# 会议室预约管理系统 — 前端体验升级方案（含极强保护约束）

## Context（为什么做这件事）

当前前端已可运行（登录/注册/布局/员工页/管理员页/axios 封装/路由守卫全部打通），构建通过。但存在三类问题：
1. **视觉**：无统一主题变量、侧边栏不可折叠、无面包屑、卡片层级弱、表格可读性一般、状态色不统一（驳回=橙/取消=红，与规范相反）。
2. **体验**：预约表单仅做了「过去时间」校验，缺工作日、结束>开始、时段冲突预校验、自动回填、长度限制；预约列表筛选维度少、无批量审批、无日历视图。
3. **功能缺口**：无工作台 Dashboard、无日历日程视图、会议室管理无卡片预览/批量启停/删除前端预校验、无本人操作记录入口。

目标：**只做前端增强，不改任何后端契约与原有业务逻辑**，让项目达到可放进简历的完成度，并补齐一份详细 README 方便前后端对齐。

## 一、红线约束（本次执行全程不得违反）

- ❌ 不改任何 axios 请求函数 / 接口 URL / 入参 DTO / 返回 VO 字段名 / 枚举值（`resStatus`、`roomId`、`startTime`、`endTime`、`status` 严格不变）。
- ❌ 不重命名 / 修改 / 删除任何已有变量、const、函数名、props、响应式数据。
- ❌ 不改原有权限判断、登录/JWT 逻辑、路由守卫、原有业务判断代码。
- ❌ 不改状态枚举映射：待审批 `0` / 已通过 `1` / 已驳回 `2` / 已取消 `3`；`room.status` 0 不可用 / 1 可用。
- ✅ 只**新增**：前端校验、视图渲染、template 标签、scoped css；新增变量/函数一律自命名（前缀 `ux`/`stat` 等），不复用已有业务变量。
- ✅ 新增仪表盘/日历**只复用清单内已有 GET 接口**，不新增任何后端请求。
- ✅ 一次只处理**单个文件**；每步先列清单、再改动、最后给出「原有（原样）/ 新增」对照。

## 三、前后端契约对照（只读，严禁改动）

| 模块 | 方法 & 路径 | 入参 | 返回关键字段 |
|---|---|---|---|
| 认证 | POST `/api/login` | `{username,password}` | `{token,userId,username,role}` |
| 认证 | POST `/api/register` | `{username,password,nickname}` | - |
| 预约 | POST `/api/booking/submit` | `{roomId,startTime,endTime,title,reason}` | - |
| 预约 | POST `/api/booking/approve` | `{bookingId,status,rejectReason}` | - |
| 预约 | DELETE `/api/booking/cancel/{id}` | path id | - |
| 预约 | GET `/api/booking/admin/page`｜`/user/page`｜`/admin/query`｜`/user/query` | `pageNum,pageSize,roomId,resStatus,startTime,endTime` | `Page{records,total}`，记录见 BookingVO |
| 会议室 | GET `/api/room/page`｜`/api/room/list` | 分页参数 | `Page` / 数组 |
| 会议室 | POST `/add`、PUT `/update`、DELETE `/delete/{id}`、PUT `/enable/{id}`、PUT `/disable/{id}` | - | - |
| 用户 | GET `/api/user/page`；PUT `/role`、`/status`、`/resetPassword` | `{id,role}`/`{id,enabled}`/`{id,password}` | - |
| 日志 | GET `/api/log/page` | `pageNum,pageSize` | `Page`，OperationLog |

**BookingVO**：`id,roomId,roomName,userId,username,startTime,endTime,resStatus,rejectReason,title,reason,createTime`
**MeetingRoom**：`id,roomName,capacity,location,description,status,createTime`（无设备/图片字段 → 卡片占位）
**SysUser**：`id,username,nickname,phone,role,enabled,createTime`
**OperationLog**：`id,userId,username,operateType,content,method,ip,costTime,createTime`
**枚举**：`resStatus` 0/1/2/3；`room.status` 0/1；`role` 0 员工 / 1 管理员；`user.enabled` 1 正常 / 0 禁用。
响应统一体：`Result{code,msg,data}`，成功 `code=200`；分页 `data=Page{records,total}`。

## 四、已知限制（写入 README，避免前后端误判）

1. 员工端无法查询他人占用 → 预约冲突预校验仅覆盖「本人同会议室时段重叠」，最终以**后端校验**为准。
2. `GET /api/log/page` 仅管理员且**无按用户过滤参数** → 「本人操作记录」弹窗仅对管理员开放，且为**当前页前端筛选**，非全量精确统计。
3. 会议室无「设备 / 图片」字段 → 卡片视图使用占位图与设备标签占位，**不新增后端字段**。
4. 员工端 `GET /api/room/page` 无权限 → 工作台「会议室总数」对员工降级为「可用会议室数」。
5. 批量审批/批量启停为**前端并发调用**既有单条接口（`Promise.all`），非新增批量后端接口。

## 五、风险与取舍

- 追加菜单项 / 路由 / 状态可见性属**新增性修改**，diff 中会显式标注「新增」并与「原有」区分。
- 所有新增逻辑与既有业务解耦：新增变量统一 `ux*` 前缀、新增函数统一 `ux*` 命名，绝不复用既有业务变量。
- 每步完成后立即 `npm run build`，避免累积到结尾才发现问题。
